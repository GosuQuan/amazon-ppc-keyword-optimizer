# 原型对标技术拆解（承接《原型测试工作流知识库》）

依据知识库 P0–P1 清单的实现拆解。每项：改动文件、验收标准、边界。

## D1 登录页免登录示例入口（P0）

- 文件：`frontend/login.html`、`frontend/login.js`
- 方案：登录卡下方增加「先看示例演示」链接，指向 `/workflow.html?demo=1`；工作台 JS 检测参数后自动触发已有的 `load-demo` 按钮。
- 验收：未登录用户可从登录页一键看到示例方案的完整调用过程；登录流程本身不变。
- 边界：示例仍消耗积分（现有 demo 计费 1 积分不变），不伪装成免费。

## D2 仪表盘行动导向（P0）

- 文件：`frontend/dashboard.html`、`frontend/dashboard.js`、`frontend/workflow.css`
- 方案：问候语下增加三个行动卡（开始新方案 / 继续最近方案 / 载入示例），各带一句话说明；数据卡与方案列表下移。
- 验收：三个行动入口可点击且指向正确；无方案时「继续最近」显示禁用态与原因。
- 边界：不新增后端接口，纯前端路由。

## D3 工作台步骤状态高亮（P0）

- 文件：`frontend/workflow.html`、`frontend/workflow.js`
- 方案：步骤条 `ol.steps` 各项按状态着色（已完成 ✓ / 进行中高亮 / 未开始灰），依据方案生命周期推导：无方案→步骤1；有方案未导出→步骤2；已导出未执行→步骤3；已执行未复盘→步骤4；已复盘→步骤5。点击步骤滚动到对应面板。
- 验收：载入示例后步骤 1、2 变完成态，步骤 3 进行中；完成复盘后全部完成。
- 边界：状态是前端推导的近似，不写入后端。

## D4 方案表格化（P1）

- 文件：`frontend/dashboard.js`、`frontend/workflow.css`
- 方案：最近方案渲染为 `<table>`：ASIN、状态、可核对花费、时间。
- 验收：表格在无数据时显示空态文案；链接仍走 `planLink()`。

## D5 结论摘要卡（P1）

- 文案：工作台分析看板顶部插入「结论摘要」，汇总动作数 / 阻断数 / 优先级分布 / 建议先处理哪类。
- 依据：方案 JSON 的 actions 已含 kind、prio、exportable、blocking_reasons。
- 边界：摘要为规则聚合，不引入模型调用。

## D6 导出条件醒目化（P1）

- 文案：导出面板顶部常显「可导出 N / 总 M」与未满足原因列表（未批准、被阻断、缺 Bulk）。
- 验收：阻断列表与后端 `export_readiness` 一致。

D1 → D2 → D3（P0 一次提交）；D4 → D5 → D6（P1 一次提交）。每项完成后在浏览器验证（本地服务 + 截图），并同步《产品白皮书》「近期验证与边界」。

## D17 导入帮助块（2026-11-02，回应插件门槛暴露的短板）

YICOPY 用「浏览器插件 + 网页」解决数据获取，我们是纯服务端、用户必须手动去后台导 CSV。插件形态短期做不了，但可以让手动导出**不出错**：工作台导入区增加可折叠的「不知道怎么导报表？」帮助块，写明：

- 搜索词报告必须包含的列（中英文表头都认，与 `ALIASES` 一致）
- 可选但有用的列（日期、账户、站点、币种、ASIN），并说明报告里有这些列时会与填写的上下文逐一比对、不一致直接失败
- 约束：先按单个 ASIN 筛选、周期建议 30–60 天且连续、不要有同维度同周期重复行
- **明确不冒充知道后台菜单位置**：不同站点/语言/改版会变，请用户以自己账户为准；缺列时系统会列出缺少哪些列

配套 `frontend/tests/import-help.test.cjs` 4 项：帮助文案必须覆盖后端 `parse_search` 里 `required` 的每一列（直接从 service.py 解析，后端改列会导致测试失败）、必须写明单 ASIN 与周期约束、不得编造后台点击路径；另加一条防止解析为空导致测试空过。

## D19 批量报告预检（2026-11-02）

紧接 D18：真实示例里 41 个动作被阻断，原因正是缺 `ad_group_id`/`campaign_id`。现在上传 Bulk 时也做预检，分两级：

- **必需**：Entity、广告活动、广告组、关键词、匹配类型——缺了这份文件不会被采用。
- **建议**：Campaign ID、Ad Group ID、Keyword ID、Bid——缺失时动作仍会生成，但**不能导出草稿**。

真实文件验证：
- 完整列 →「批量报告预检通过：实体、名称、ID 与出价列都已找到。」
- 缺 ID 与出价 →「缺少 campaign_id、ad_group_id、keyword_id、bid。动作仍会生成，但缺少实体 ID 或真实出价时不能导出草稿。」

两级文案都带"最终以服务端校验为准"。测试 10 项（含 Bulk 四类场景）。

## D20 可选报告预检（2026-11-02，预检收尾）

补齐推广商品报告与广告位报告的预检，四份报告全部覆盖：

| 报告 | 必需列 | 缺失后果 |
|---|---|---|
| 搜索词（必填） | 客户搜索词、广告活动、广告组、关键词、匹配类型、花费、销售额、订单、点击 | 无法生成方案 |
| 批量 Bulk（可选） | Entity、广告活动、广告组、关键词、匹配类型（+建议 ID/Bid） | 无 ID/出价则动作不可导出 |
| 推广商品（可选） | ASIN、广告活动、广告组 | 该报告不被采用 |
| 广告位（可选） | Placement、广告活动 | 该报告不被采用 |

可选报告的提示会额外说明"它是可选的，不上传也能生成方案"，避免用户误以为必须补齐。真实文件四种组合均验证（通过 / 缺 asin / 通过 / 缺 placement）。测试 13 项。

### 修复：TSV 批量报告曾被误判缺列（2026-11-02）

预检最初**只按逗号切分**，但批量报告输入框接受 `.csv,.tsv`，而亚马逊后台导出的 Bulk 通常就是 **Tab 分隔**。上传 TSV 会被误判成"缺少全部必需列"，给出错误警告——一个会把用户带偏的假警报。

现在按实际出现次数选择分隔符（Tab 多于逗号则按 Tab 切）。真实 TSV 文件验证：「批量报告预检通过：实体、名称、ID 与出价列都已找到。」测试 15 项（新增 TSV 识别 + 逗号仍优先）。

### 验证：复盘解读句用真实后端数据核对（2026-11-02）

此前 `reviewConclusion()` 只有单元测试，**没用真实后端数据验证过单位**——若 `acos` 是小数（0.5）而非百分比，会错误显示成「ACOS 由 0.5%…」。

现走通完整 API 流程（建方案 → 批准 → 导出 → 登记执行 → 周期复盘）取得真实复盘对象并注入页面函数，实测输出：
